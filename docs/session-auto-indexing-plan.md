# Session 自动索引与片段容量

状态：已实现。符合资格的 Session 自动纳入索引，用户可以主动剔除。容量按每个 Agent 的
Session 片段总数管理；实际可纳入的 Session 数取决于完整分块结果。

## 1. 容量与纳入规则

| Agent | 默认 Session 片段预算 |
| --- | ---: |
| Codex | 5,000 |
| Claude Code | 5,000 |
| Cursor | 5,000 |
| OpenCode | 5,000 |
| 合计 | 20,000 |

这是 MVP 初始资源预算，工程负载验证不代表该数值具有最优检索质量。配置、校验和命令以
`src/server/config.ts` 与 README 为准。可按 Agent 调整预算，重启后生效：

```bash
agent-memory config set sessionFragmentLimits.codex 10000
```

- 沿用现有目录、subagent、可见消息、完整 turn、最小正文与敏感内容过滤规则。
- 候选元数据持续保存，通过分页和持久化游标处理。完成当前发现范围后，按来源更新时间
  降序、稳定 ID 升序处理候选，避免为最终处于容量外的历史 Session 先生成向量。
- 文件来源使用文件修改时间排序，OpenCode 使用显式更新时间；这只是来源排序，消息时间
  继续只采用原始消息的显式元数据。
- 已写入文本索引的全部 Session 片段均计入占用，包括向量等待、生成中或失败的片段。
  单写入者在同一事务内核算和提交，因此当前预留片段数为零。
- 一个 Session 完整纳入或保持等待，不截断正文、不丢弃部分 turn。单个 Session 超过其
  Agent 总预算时显示明确原因；来源内容或预算改变后重新检查。
- 新来源按优先级替换较旧来源，需要时释放多个旧 Session 的派生片段。容量外来源保留
  元数据与审计，显示“容量等待”；已有选取决定的审计完整保留。
- 用户剔除会删除派生片段并停止检索参与，扫描、重启和重建保留该决定。恢复重新读取当前
  来源并遵守相同预算，容量允许时补位。
- Memory 继续自动增量索引；其规模和资源使用单独记录。

## 2. 启动与后台调度

HTTP 监听成功后才启动后台扫描。健康接口独立于模型下载和向量准备，已保存的索引可继续
检索。首次启动仍需完成发现、分块和推理，状态接口如实显示进度。

- 目录按稳定路径游标增量遍历，文件属性顺序读取。每步处理一个文件或目录；不同 adapter
  轮询，每步结束后让出事件循环。单目录的 `readdir` 结果仍需在内存排序。
- 不合格、损坏与空目录同样推进游标。范围不完整、读取失败或达到目录批次上限时，保留
  进度；只有完整完成对应范围后才判定来源消失。
- 保存 Session 资格检查缓存，依据文件大小、修改时间和规则版本复用；24 小时后重新检查
  正文。真正索引或恢复时重新读取来源并核对内容指纹。
- 候选发现与文本索引分阶段处理。待处理来源使用索引和时间/ID 游标分页，防止大量等待
  来源导致重复全表扫描；文本阶段每步处理一个来源。
- 文本事务完成后才处理向量，每批最多 16 个片段，后台推理批次串行执行并逐批保存。
  多批次来源在持久状态中续跑，失败保留诊断并退避重试。
- 剔除、恢复和关闭在处理步骤之间执行。关闭等待当前步骤与已接受的操作，不等待自动
  积压全部清空。向量提交前再次核对来源资格和指纹，失效批次不重新写入。
- worker 状态记录步骤耗时、最大耗时及超过 50 ms 的步骤数；这些是步骤墙钟耗时，包含
  异步推理等待，不能代替事件循环延迟或 HTTP 响应时间。

## 3. 持久化与检索

- 递增 migration 保存资格缓存、片段估计、容量等待原因、失败重试时间和派生片段计数。
  daemon 保持唯一写入者，来源文件只读，重建不清除用户决定与审计。
- 片段使用 FTS rowid 定位删除，避免每次淘汰来源都扫描完整 FTS；没有片段的候选直接跳过
  删除。降低预算时分步释放较旧来源，避免升级或启动时长时间同步清理。
- 向量按模型标识和输入哈希复用；重启只补缺失批次。模型按需加载，关闭时释放。
- 语义支路每批读取 128 个向量，批次间让出事件循环；关键词支路分页读取元数据。
  只为最终有界候选读取正文，保留硬过滤、原始关键词排名、RRF、重排深度和 turn 多样化。
  异步扫描或重排后再次校验来源可用性与内容指纹。
- 检索仍执行精确扫描，其计算成本随向量数量增长；并发请求各自持有候选预算。20,000 个
  768 维 Float32 向量约 58.6 MiB，这不包含正文、Memory、模型、推理张量与运行时对象。
- `GET /api/index/status` 的 `sessionCapacity` 按 Agent 返回预算、占用、预留、已纳入与等待
  Session 数；管理页区分等待处理、容量等待、超预算、用户剔除和索引失败。

## 4. 验证与复现

功能覆盖自动纳入、不同 Agent 的片段预算、完整 Session 替换、超长来源、剔除补位、恢复、
已有决定保留、中断恢复、失效批次、失败退避和重建调度。检索使用完整排序对照验证有界
候选实现，Web 使用真实服务验证自动纳入、剔除后无命中、恢复与 hybrid 搜索。

合成调度负载使用隔离数据库和生成的片段，不调用来源正文解析、tokenizer、模型或 HTTP。
每个候选生成一个片段，四个 Agent 均分候选，结果包含源码指纹、计时、RSS 与容量统计：

```bash
caffeinate -i node --import tsx scripts/verify-session-load.ts 1000 10000 100000
```

结果保存在已忽略的 `.agent-memory-share-mcp/verification/session-auto-indexing/`。
真实本地模型与浏览器验证使用单独的合成来源及临时服务，模型远程请求关闭；分别报告健康
可用时间、健康响应、首次推理和重启复用，不能用无模型调度数据证明推理性能。

大规模目录、长正文、模型冷加载和同时查询仍会影响耗时。发生长时间调度间隔的原始测量
保留供审计，另行完整重跑；不扣除估计暂停时间，不以合成数据推断真实语料召回质量。
